# 1. Purpose

This document is the top-level map of the project documentation.

It defines:

- the major project areas;
- the relationships between them;
- the purpose of each documentation layer;
- the authoritative location of project knowledge;
- the flow from scientific research to specification, implementation,
  validation and certification;
- the mechanism by which new knowledge is propagated through the project.

This document is intentionally architectural.

Detailed requirements, scientific findings, implementation specifications
and validation procedures belong in the documents referenced by this map.

---

# 2. Project Objective

The project investigates, scientifically and experimentally, textual
watermarking, watermark detection, AI-generated-text detection and textual
transformation.

The project must support:

- multilingual research;
- reproducible experimentation;
- preservation measurement;
- detector and watermark evolution;
- rigorous validation;
- continuous scientific updating;
- maintainable implementation architecture.

The project is designed so that research conclusions can evolve without
requiring the entire project documentation or software architecture to be
discarded and rebuilt.

---

# 3. Core Principle

The project is an evidence-driven system.

Scientific evidence must be traceable through the following lifecycle:

SOURCE
→ RESEARCH
→ EVIDENCE
→ ANALYSIS
→ REQUIREMENT
→ ARCHITECTURE
→ IMPLEMENTATION
→ EXPERIMENT
→ VALIDATION
→ DECISION

No important project decision should depend solely on undocumented intuition.

Research findings, assumptions, decisions, implementation choices and
validation results must remain distinguishable.

# 19. Propagation Rule

When a new fact, discovery, experiment or decision materially affects the
project, it must be propagated.

The responsible process is:

DISCOVERY
→ REGISTER
→ CLASSIFY
→ IDENTIFY IMPACT
→ QUEUE DOCUMENTATION CHANGES
→ UPDATE AFFECTED DOCUMENTS
→ VALIDATE CONSISTENCY

The existence of a new research document does not automatically mean the
project documentation is updated.

A research finding may require changes to specification, architecture,
validation, security, data or operations.

# 20. Documentation Consistency

The documentation system must maintain consistency between:

- maps;
- requirements;
- assumptions;
- decisions;
- research findings;
- architecture;
- validation;
- security;
- operations.

When inconsistency is discovered, it must be explicitly resolved.

Examples of consistency failures include:

- a referenced file does not exist;
- a requirement is defined but has no validation method;
- a validation criterion has no originating requirement;
- an architectural component has no documented purpose;
- a decision contradicts a current specification;
- a deprecated component remains required by active documentation.

# 21. Change Management

Changes may originate from:

- scientific literature;
- experimental results;
- new detectors;
- new watermark methodologies;
- new languages;
- security discoveries;
- implementation constraints;
- operational failures;
- dependency changes;
- newly identified risks.

Every material change must have traceability.

A change should identify, where applicable:

- source;
- reason;
- affected documents;
- affected components;
- validation consequences;
- compatibility consequences;
- deprecation consequences.

---

# 22. Future-Proofing

The project must be designed to accommodate:

- new watermark families;
- new watermark detectors;
- new AI detectors;
- new languages;
- new datasets;
- new evaluation methodologies;
- new scientific findings;
- new security requirements;
- retirement of obsolete components.

New functionality should be introduced as modular additions wherever
possible.

Obsolete functionality must be removable without destabilizing unrelated
components.

The architecture must not assume that the current detector or watermark
landscape is permanent.

# 23. Component Lifecycle

Project components should support the following lifecycle:

PLANNED
→ EXPERIMENTAL
→ VALIDATED
→ ACTIVE
→ DEPRECATED
→ RETIRED

A component may also become:

SUPERSEDED

when replaced by a superior methodology.

Lifecycle transitions must be documented.

Deprecation must preserve:

- historical identity;
- reason for deprecation;
- final supported version;
- known limitations;
- successor information where applicable;
- migration implications.

---

# 24. Offline Execution Principle

The execution environment is conceptually separated from the research and
development environment.

Research and development may use external resources where permitted.

The operational software may be required to execute without AI services or
other cloud inference dependencies.

This distinction must remain explicit throughout:

- architecture;
- development;
- operations;
- validation;
- certification.

Any external detector or cloud service used during research or validation
must be treated as an external dependency and its effect must be documented.

---

# 25. External Services

External services may be used where scientifically justified.

The project must explicitly record:

- what service is used;
- why it is used;
- what data leaves the local environment;
- how its result is incorporated;
- how its availability affects the system;
- whether an equivalent local fallback exists;
- whether its behavior can change independently of the project;
- the date and version, where available.

External results must be distinguishable from locally reproducible results.

---

# 26. Autonomous Development

The software may be developed and maintained by AI-assisted development
systems.

This does not imply that the operational software itself uses AI.

The development process and execution architecture are separate concerns.

Autonomous development must operate inside the constraints established by:

- governance;
- scientific specification;
- architecture;
- security;
- validation;
- certification.

Autonomous development is intended to reduce repetitive manual work, not to
delegate uncontrolled scientific or security decisions.

---

# 27. Development Safety Boundary

Autonomous development must not silently change:

- scientific acceptance criteria;
- security boundaries;
- data handling policy;
- privacy requirements;
- architectural invariants;
- certification criteria;
- project objectives.

Changes of this class require explicit project-level authorization.

Routine implementation, testing, refactoring and documentation maintenance
may be automated when they remain within approved boundaries.

Automated agents must detect and report uncertainty rather than silently
inventing missing requirements.

---

# 28. Quality Gates

Major project transitions require evidence.

Examples:

RESEARCH → SPECIFICATION

requires sufficient scientific evidence.

SPECIFICATION → ARCHITECTURE

requires architectural consistency.

ARCHITECTURE → DEVELOPMENT

requires implementability.

DEVELOPMENT → VALIDATION

requires reproducible builds and tests.

VALIDATION → CERTIFICATION

requires satisfaction of certification criteria.

CERTIFICATION → RELEASE

requires release integrity and complete required evidence.

A failed quality gate must not be hidden by modifying the acceptance criterion
without recording the change.

---

# 29. No Premature Completion

The project must not be declared complete merely because:

- the software runs;
- tests pass;
- documentation exists;
- a detector produces a desired result;
- an experiment produces a favorable outcome.

Completion requires satisfaction of the scientifically defined acceptance
criteria.

Known limitations must remain visible.

A system may be operationally usable while still having explicitly documented
scientific limitations.

---

# 30. Continuous Reassessment

The project must support periodic reassessment of:

- scientific evidence;
- detector landscape;
- watermark landscape;
- multilingual coverage;
- benchmarks;
- dependencies;
- security assumptions;
- operational requirements.

A previously valid conclusion may become obsolete.

Reassessment should be triggered especially by:

- important new papers;
- new detector methodologies;
- new watermark methodologies;
- major model releases;
- new languages or tokenization methods;
- significant benchmark changes;
- security discoveries.

---

# 31. Documentation Maintenance

Documentation is treated as part of the system.

It must therefore be:

- versioned;
- internally consistent;
- traceable;
- modular;
- maintainable;
- auditable.

New knowledge must not be allowed to accumulate only in chat history or
developer memory.

Documentation should contain enough information for a future developer or
development agent to reconstruct the project's current reasoning.

---

# 32. Autonomous Documentation Review

Before a major documentation tranche is considered complete, an automated
review should check:

- broken internal references;
- missing referenced files;
- contradictory statuses;
- orphaned requirements;
- unresolved placeholders;
- duplicate identifiers;
- inconsistent terminology;
- stale dependency references;
- missing change-queue entries;
- map/document inconsistencies;
- malformed Markdown;
- duplicated sections;
- accidental generated content;
- incomplete documents.

The exact review mechanism is defined later in the development and governance
documentation.

The review must be repeatable and executable without relying on human memory.

# 33. Documentation Change Queue as Safety Net

When an idea emerges during research or implementation but cannot immediately
be integrated into the correct document, it must be placed in:

`docs/00-project/DOCUMENTATION-CHANGE-QUEUE.md`

This prevents useful ideas from being lost while avoiding uncontrolled edits
during active work.

The queue is also the mechanism for recording cross-document changes that
must be propagated later.

A queue entry should identify:

- originating document;
- proposed destination;
- reason;
- priority;
- dependencies;
- validation required.

---

# 34. Knowledge Backlog as Safety Net

When a question cannot yet be answered reliably, it belongs in:

`docs/00-project/KNOWLEDGE-BACKLOG.md`

It must not be converted into an unsupported requirement.

Knowledge backlog entries should distinguish:

- unknown;
- suspected;
- partially evidenced;
- experimentally unresolved;
- blocked by unavailable data;
- blocked by unavailable tooling.

---

# 35. Decision Log as Safety Net

When a choice affects architecture, scientific methodology, validation or
project scope, it belongs in:

`docs/00-project/DECISION-LOG.md`

The decision should include:

- decision;
- date;
- rationale;
- evidence;
- alternatives considered;
- consequences;
- affected documents;
- reversal conditions where applicable.

---

# 36. Assumption Registry as Safety Net

When the project must temporarily operate under an unverified premise, the
premise belongs in:

`docs/00-project/ASSUMPTION-REGISTRY.md`

Assumptions should have:

- identifier;
- statement;
- reason;
- evidence status;
- risk;
- owner or responsible process;
- validation method;
- current status.

Assumptions should be retired when they become established facts, disproven
claims or unnecessary premises.

---

# 37. Project State Model

The project should conceptually progress through:

RESEARCH
→ SPECIFICATION
→ ARCHITECTURE
→ IMPLEMENTATION
→ EXPERIMENTATION
→ VALIDATION
→ CERTIFICATION
→ OPERATION
→ CONTINUOUS RESEARCH

The final state is not static.

Operation feeds new observations back into research and validation.

Scientific developments can therefore cause the project to return to earlier
states.

This is expected behavior rather than a project failure.

---

# 38. Top-Level Completion Condition

The project is considered complete for a release only when:

- scientific requirements are defined;
- relevant evidence is documented;
- architecture satisfies requirements;
- implementation satisfies architecture;
- validation satisfies acceptance criteria;
- security requirements are satisfied;
- data provenance is documented;
- operational procedures exist;
- certification evidence exists;
- known limitations are explicitly recorded;
- required documentation is internally consistent.

Completion is therefore release-specific rather than permanent.

---

# 39. Final Principle

The project is not a one-time software build.

It is a maintainable scientific and engineering system whose knowledge,
requirements, architecture, implementation and validation must be able to
evolve together.

The documentation architecture exists to make that evolution controlled,
traceable and reviewable.
